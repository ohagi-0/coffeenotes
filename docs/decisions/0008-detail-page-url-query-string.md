# 0008: 詳細ページの URL はクエリ文字列（`/beans?id=…`）にする

- 日付: 2026-09-22
- ステータス: 決定
- 関連要件: F-LIST-4、F-LOG-7、F-MAP-2、REQUIREMENTS.md §13.2 N-1（静的出力）

## 背景

Phase 6 で Capacitor により iOS / Android アプリ化する方針（ADR 0002）。Capacitor は Next.js の静的出力（`output: 'export'`）を包むため、画面はすべてビルド時に生成できる形でなければならない。

2026-09-22 に現状のコードを複製して `output: 'export'` でビルドしたところ、以下が確認できた。

- 現状の画面はそのまま静的出力できる。
- `/api/*` の Route Handler は静的出力から自動で除外される（Web 版は Vercel が配信し、アプリ版は本番 URL 経由で呼ぶ。既存の `apiUrl()` の設計どおり）。
- 動的ルート `src/app/(app)/beans/[id]/page.tsx` を置くと `Page "/beans/[id]" is missing "generateStaticParams()"` でビルドが落ちる。豆や記録の ID はユーザーが登録して初めて決まるため、`generateStaticParams` で事前列挙することはできない。

## 選択肢

| | 内容 | 評価 |
|---|---|---|
| A | クエリ文字列 `/beans?id=…` にする | 静的出力でそのまま動く。コードは Web / アプリで 1 系統。URL の見た目だけ劣る |
| B | `/beans/[id]` のまま進め、Phase 6 で書き換える | 全画面のリンクと遷移を後から書き換える手戻り |
| C | アプリを Vercel のサイトを表示するだけの箱にする | 静的出力が不要になるが、オフライン閲覧（F-MISC-1 の Must）が成り立たず、Apple の審査で「Web サイトの包み」として却下されるリスク |
| D | Web は `[id]`、アプリはクエリの 2 系統 | リンクを二重に保守することになる |

## 決定

A を採用する。

- 豆詳細: `/beans?id=<uuid>`
- 記録詳細・編集: `/logs?id=<uuid>`（記録作成は従来どおり `/logs/new`）
- 店詳細: `/shops/detail?id=<uuid>`（`/shops` は一覧 S6 のまま）
- `src/app/` 配下に `[id]` などの動的セグメントを置かない。
- URL の組み立ては `src/lib/routes.ts` の `routes.bean(id)` などを必ず通し、画面側で文字列を組み立てない。
- 詳細ページは `useSearchParams()` で `id` を読む。静的出力では `Suspense` 境界が必須（`src/app/auth/callback/page.tsx` と同じ形）。`id` が無い・不正なときは「見つかりません」の状態を出す。
- 将来「豆を公開して共有する」機能を作る場合は、`/share/…` のような公開専用ページを別に用意する。本決定は本人だけが見る内部ページに関するもの。

## 理由

- 記録は本人にしか見えず（RLS）、共有機能は将来扱い（REQUIREMENTS.md §1.4）なので、URL を人に渡す場面が無い。ホーム画面から開く PWA やアプリには URL バーが無く、見た目の差は誰にも見えない。
- S4 / S5 の画面実装が未着手の今なら、変更は設計書の数行で済む。B は Phase 6 での手戻りが大きく、C はアプリ化の目的（オフライン閲覧・ストアの信頼感）を半分失う。
- 「複数の人に使ってもらう」前提でも結論は変わらない。各ユーザーのデータが分かれている限り、URL の形は利用者体験に影響しない。
