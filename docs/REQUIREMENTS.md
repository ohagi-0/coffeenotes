## 1. 背景と目的

### 1.1 背景

スペシャルティコーヒーのロースターやカフェでは、豆ごとに「テイスティングカード」（産地・品種・精製方法・フレーバー・味覚チャート・価格など）が配布される。飲んだ豆の情報を残しておきたいが、カードは紙のまま溜まり、あとから「あの店で飲んだライム系の豆は何だったか」を探せない。

### 1.2 目的

飲んだコーヒー豆の情報を **カード写真から半自動で取り込み**、**飲んだ店・自分の好み評価** と紐づけて蓄積し、**一覧・検索・地図** から振り返れるようにする。

### 1.3 ゴール（成功の定義）

| # | ゴール | 測り方 |
|---|---|---|
| 1 | カード1枚の登録が1分以内で終わる | 撮影→OCR→確認→保存までの所要時間 |
| 2 | 過去に飲んだ豆を産地・フレーバー・店名で探せる | 検索機能の利用 |
| 3 | 自分の好みの傾向（高評価の産地・精製方法など）が見える | 統計画面の提供 |
| 4 | 個人利用の範囲ではランニングコストをほぼゼロに抑える | 月額コスト試算（§9） |

### 1.4 スコープ外（初版では扱わない）

- 豆の販売・EC 連携
- ロースターとの公式データ連携（QRコードの先の商品ページ取得など）
- SNS 的な公開タイムライン、フォロー機能
- ネイティブアプリ（App Store / Google Play 配信）

## 2. 利用者とユースケース

### 2.1 利用者

| 利用者 | 説明 |
|---|---|
| 一般ユーザー | 自分のコーヒー記録を登録・閲覧する。他人の記録は原則見えない |
| 管理者（開発者本人） | 全体の利用状況確認、不正データの削除 |

複数ユーザーを想定するが、初版は **「各ユーザーが自分のデータだけを扱うプライベートな記録帳」** とし、共有機能は将来拡張とする（§10）。

### 2.2 主要ユースケース

| UC | シナリオ |
|---|---|
| UC1 カードから登録 | カフェでカードをもらう → 表・裏を撮影 → 自動抽出された項目を確認・修正 → 店をタグ付け → 星評価とメモを入力 → 保存 |
| UC2 手入力で登録 | カードが無い豆を、項目を手入力して登録 |
| UC3 振り返り | 一覧を「産地」「精製」「評価順」で絞り込み、過去の記録を見る |
| UC4 地図で探す | 地図上でタグ付けした店を見て、そこで飲んだ豆一覧を開く |
| UC5 好みの分析 | 星4以上の豆に多い産地・精製方法・フレーバーを確認する |
| UC6 同じ豆を再び飲む | 既に登録済みの豆を別の日・別の店で飲んだとき、豆情報を再入力せずに記録だけ追加する |
| UC7 自宅で淹れる | 買ってきた豆を自宅で挽いて淹れる。挽き目・湯温・レシピを記録し、同じ豆でレシピ違いの味を比べる |
| UC8 自家焙煎 | 生豆から自分で焙煎する。生豆情報と焙煎条件（日付・時間・焙煎度）を記録し、その豆を UC7 で飲む |

## 3. 機能要件

優先度: **Must**（初版必須）/ **Should**（初版に入れたい）/ **Could**（あれば良い）/ **Later**（将来）

### 3.1 認証・ユーザー管理

| ID | 機能 | 優先度 | 詳細 |
|---|---|---|---|
| F-AUTH-1 | ログイン | Must | メール+マジックリンク と Google ログインの両方を提供（決定）。パスワード管理は持たない。同じメールアドレスなら両方式で同一アカウントに紐づける |
| F-AUTH-2 | データ分離 | Must | ユーザーは自分のデータのみ読み書き可能（DB 側で行レベルセキュリティを強制） |
| F-AUTH-3 | アカウント削除 | Should | 自分のデータ（画像含む）を全削除できる |

### 3.2 豆（Bean）情報の登録

カードに書かれている情報を保持する。今回のサンプルカード（KIELO COFFEE / Lusitania Lime Geisha）から抽出した項目を基準とする。

| ID | 項目 | 型 | 必須 | 優先度 | サンプル値 |
|---|---|---|---|---|---|
| F-BEAN-1 | 豆名 | 文字列 | 必須 | Must | Lusitania Lime Geisha |
| F-BEAN-2 | ロースター | 文字列（マスタ参照） | 必須 | Must | KIELO COFFEE |
| F-BEAN-3 | 生産国 | 文字列（選択+自由入力） | 任意 | Must | Colombia |
| F-BEAN-4 | 地域 | 文字列 | 任意 | Must | Caicedonia, Valle del Cauca |
| F-BEAN-5 | 品種 | 文字列 | 任意 | Must | Geisha |
| F-BEAN-6 | 精製方法 | 文字列 | 任意 | Must | Lime infused |
| F-BEAN-7 | 標高 | 整数（m） | 任意 | Must | 1650 |
| F-BEAN-8 | フレーバーノート | 文字列配列 | 任意 | Must | Lime, Bergamot, Laurier |
| F-BEAN-9 | 説明文 | 文字列（複数行） | 任意 | Should | ライムを思わせるシトラス系の… |
| F-BEAN-10 | 味覚チャート | 整数 1〜5 ×5軸 | 任意 | Should | Flavor 5 / Sweetness 3 / Acidity 5 / After taste 3 / Body 3 |
| F-BEAN-11 | 豆価格 | 整数（円）+ 単位グラム | 任意 | Should | ¥3,800 / 100g |
| F-BEAN-12 | カード画像（表・裏） | 画像ファイル | 任意 | Must | 2枚まで。原本として保持 |
| F-BEAN-13 | 参照URL | 文字列 | 任意 | Could | カードの QR コードを読み取って格納 |
| F-BEAN-14 | 焙煎度 | 選択（浅/中/深） | 任意 | Could | カードに無い場合はユーザー入力 |
| F-BEAN-15 | 入手区分 | 選択（購入 / 自家焙煎） | 必須 | Must | 自家焙煎の場合はロースターを「自分」とし、F-ROAST 系の記録を持てる |

味覚チャートの軸名は固定（Flavor / Sweetness / Acidity / After taste / Body）とし、カードに無い軸は未入力を許容する。

**入力経路は 3 つ**（カード読み取り / 手入力 / 登録済みから選択）で、どの経路でも同じフォームに落ちる。カードが無い豆（量り売り、もらい物、自家焙煎）は手入力で完結する。

### 3.3 カード読み取り（OCR）

| ID | 機能 | 優先度 | 詳細 |
|---|---|---|---|
| F-OCR-1 | 撮影・アップロード | Must | スマホカメラで撮影、またはギャラリーから選択。表・裏を続けて撮れる |
| F-OCR-2 | 項目の自動抽出 | Should | 画像から §3.2 の各項目を推定し、フォームに **プリフィル** する（確定はユーザー） |
| F-OCR-3 | 味覚チャート読み取り | Could | ドットの濃淡（塗り／未塗り）から 1〜5 を推定する |
| F-OCR-4 | QR コード読み取り | Could | 参照URLとして格納する |
| F-OCR-5 | 抽出結果の信頼度表示 | Could | 自信のない項目を強調表示し、確認を促す |
| F-OCR-6 | 抽出方式の差し替え | Must | OCR エンジンをインターフェース越しに呼び、後から方式を変更できる構造にする（§8 で選定） |

**設計方針**: OCR は「便利な下書き機能」と位置づけ、**OCR が失敗しても手入力で登録が完結する** こと。方式が未確定でもアプリ本体の開発を止めないため、F-OCR-6 の抽象化を最初から入れる。

### 3.4 店（Shop）とタグ

| ID | 機能 | 優先度 | 詳細 |
|---|---|---|---|
| F-SHOP-1 | 店の登録 | Must | 店名・住所・緯度経度を持つ。ユーザーごとに管理 |
| F-SHOP-2 | 店の検索・選択 | Must | 過去に登録した店からインクリメンタル検索して選ぶ |
| F-SHOP-3 | 現在地から店を補完 | Should | スマホの位置情報から周辺の候補を出し、選ぶと住所・座標が入る |
| F-SHOP-4 | 店名から座標を補完 | Should | 店名・住所を入力するとジオコーディングして座標を入れる |
| F-SHOP-5 | 店の種別 | Should | 「飲んだ店（カフェ）」「買った店（ロースター）」「生豆販売店」を区別する |
| F-SHOP-6 | 店名・住所の手入力 | Must | 候補検索に出てこない店（Google にも無い個人店など）向けに、店名・住所を手打ちで登録できる。座標は住所からのジオコーディング、または地図をタップしてピンを置く（F-SHOP-7）の順で補完 |
| F-SHOP-7 | 地図タップで位置指定 | Must | 地図上を長押し／タップしてピンを置き、その座標を店に保存する。候補検索・ジオコーディングが両方失敗しても店を地図に載せられる。**記録作成の「自分で登録する」では使わず**（スマホでピンを刺すのは無理がある。2026-09-25）、店名 + 住所で登録して住所から位置を引く。ピン指定は店フォーム（登録・編集）だけに残す |

店の登録は「①候補から選ぶ → ②手入力 + 住所から座標 → ③手入力 + 地図タップ」の 3 段構えとし、どの段でも最終的に座標付きの店が作れることを保証する。座標が無い店も保存は許可し、地図には出さず一覧にだけ出す。
| F-TAG-1 | 自由タグ | Should | 記録に任意のタグ（例: `#ゲイシャ`, `#インフューズド`, `#朝`）を複数付けられる |
| F-TAG-2 | タグの候補表示 | Should | 過去に使ったタグを候補に出す |

### 3.5 記録（Log）と評価

「豆」と「飲んだ・買った出来事」を分ける。同じ豆を複数回飲む UC6 に対応するため。

| ID | 機能 | 優先度 | 詳細 |
|---|---|---|---|
| F-LOG-1 | 記録の作成 | Must | 豆 × 日付 × 店 × 評価 × メモ。豆は既存から選ぶか、新規作成 |
| F-LOG-2 | 星評価 | Must | 1.0〜5.0 の 0.5 刻み（決定）。「自分の好み」を表す。UI は星の左半分／右半分タップで半星を入力 |
| F-LOG-3 | メモ | Must | 自由記述。飲んだ感想、抽出方法など |
| F-LOG-4 | 抽出方法 | Should | 選択（ハンドドリップ / エスプレッソ / アイス / その他）+ 自由入力 |
| F-LOG-5 | 飲んだ or 買った | Should | 種別フラグ。買った場合は購入量（g）を任意で持つ |
| F-LOG-6 | 写真 | Could | カップや店の写真を 1 枚添付 |
| F-LOG-7 | 編集・削除 | Must | 自分の記録を編集・削除できる。記録を消してその店の記録が 0 件になったら店も一緒に消す（2026-09-24。ライト層には「消したら消える」が分かりやすい。先に店だけ登録した場合は残る） |
| F-LOG-8 | 場所区分 | Must | 「店で飲んだ」「自宅で淹れた」を区別する。自宅の場合は店の指定を不要にする |

### 3.5.1 自宅抽出の記録（UC7）

自宅で淹れたときに、店では取れない「レシピ」を残す。すべて任意項目とし、入力しなくても記録は保存できる。

| ID | 項目 | 型 | 優先度 | 備考 |
|---|---|---|---|---|
| F-BREW-1 | 抽出器具 | 選択 + 自由入力 | Should | ハンドドリップ（ドリッパー名）/ エスプレッソ / フレンチプレス / エアロプレス / 水出し など |
| F-BREW-2 | グラインダー・挽き目 | 文字列 + 数値 | Should | 例: Comandante C40 / 25 クリック |
| F-BREW-3 | 豆量・湯量 | 整数（g） | Should | 比率（1:15 など）を自動計算して表示 |
| F-BREW-4 | 湯温 | 整数（℃） | Should | |
| F-BREW-5 | 抽出時間 | 秒 | Should | |
| F-BREW-6 | レシピメモ | 文字列 | Should | 注ぎ方など自由記述 |
| F-BREW-7 | 前回のレシピを複製 | 機能 | Should | 同じ豆の直近の記録からレシピ項目をコピーして微調整できる |
| F-BREW-8 | 豆の焙煎日・経過日数 | 日付 | Could | 購入豆の焙煎日を beans に持ち、記録時点の経過日数を表示 |

### 3.5.2 自家焙煎の記録（UC8）

「豆（beans）」に対して 0〜複数の「焙煎（roasts）」を持たせる。焙煎ごとにバッチとして扱い、その焙煎バッチを飲んだ記録（logs）が紐づく。

| ID | 項目 | 型 | 優先度 | 備考 |
|---|---|---|---|---|
| F-ROAST-1 | 焙煎日 | 日付 | Should | |
| F-ROAST-2 | 焙煎方法・器具 | 選択 + 自由入力 | Should | 手網 / 手回し / 電気焙煎機（機種名） など |
| F-ROAST-3 | 生豆投入量・焙煎後重量 | 整数（g） | Should | 減率（%）を自動計算 |
| F-ROAST-4 | 焙煎時間 | 分:秒 | Should | |
| F-ROAST-5 | 焙煎度 | 選択（浅/中浅/中/中深/深） | Should | 1ハゼ・2ハゼの有無は自由入力に含める |
| F-ROAST-6 | 焙煎メモ | 文字列 | Should | 火力の推移、狙いなど |
| F-ROAST-7 | 生豆の入手元 | 文字列（店マスタ参照可） | Should | 生豆を買った店。§3.4 の店種別に「生豆販売店」を追加 |
| F-ROAST-8 | 焙煎バッチの評価比較 | 機能 | Could | 同じ生豆の焙煎バッチごとに平均星を並べて表示 |

温度プロファイル（時系列の温度曲線）は初版では扱わない（自家焙煎に特化した既存アプリの領域。§12 参照）。

## 4. データモデル

### 4.1 エンティティ関係

```
users 1 ─── * beans        （ユーザーが登録した豆）
users 1 ─── * shops        （ユーザーが登録した店）
users 1 ─── * logs         （飲んだ／買った記録）
beans 1 ─── * logs
shops 1 ─── * logs         （logs.shop_id は NULL 可）
roasters 1 ─── * beans     （ロースター名のマスタ。ユーザー横断で共有可）
logs * ─── * tags          （log_tags 中間テーブル）
beans 1 ─── * bean_images  （表・裏）
beans 1 ─── * roasts       （自家焙煎バッチ。購入豆は 0 件）
roasts 1 ─── * logs        （logs.roast_id は NULL 可。どのバッチを飲んだか）
```

## 8. 技術選定の記録と相談事項

### 8.1 OCR 方式 — **決定: A. Claude Haiku Vision**（2026-09-21）

決定理由: 個人〜数十人規模では費用差が月数百円未満で誤差の範囲。項目振り分け・味覚チャートのドット・日本語説明文を一度に構造化でき、ロースターごとのレイアウト差にパーサ保守が不要な点を優先した。F-OCR-6 の抽象化は維持し、費用が問題になった段階で差し替え可能とする。以下は比較時の記録。

サンプルカードの読み取りで必要なのは「文字を読む」だけでなく、「Region: … / Flavor: … のように **項目へ振り分ける**」「日本語説明文と英語項目が混在する」「ドットの塗り／未塗りを数える」の 3 点。方式によって得意・不得意が分かれる。

| 観点 | A. LLM Vision（Claude Haiku 等） | B. Google Cloud Vision（Text Detection） | C. ブラウザ内 OCR（Tesseract.js） |
|---|---|---|---|
| 仕組み | 画像をそのまま送り「この JSON 形式で返せ」と指示 | 画像から文字列と座標を返す | JS ライブラリがブラウザ内で文字認識 |
| 項目への振り分け | モデルが行う（プロンプトで指定） | 自前で正規表現などを書く | 自前で書く |
| 日本語混在 | 問題なし | 対応（言語ヒント指定） | 日本語モデル読み込みが重い（数十MB） |
| 味覚チャートのドット | 読める可能性が高い（画像として判断） | 不可（文字ではない） | 不可 |
| 精度（項目単位） | 高い | 文字は高精度、振り分けは実装次第 | 中〜低（斜め撮影・影に弱い） |
| 応答時間 | 3〜8 秒 | 1〜2 秒 | 5〜20 秒（端末性能依存） |
| 実装工数 | 小（プロンプト + JSON スキーマ） | 中（パーサ実装） | 中（パーサ + モデル配信） |
| 料金（2026-09 時点） | Haiku 4.5: 入力 $1 / 出力 $5 per 100万トークン。カード1枚（画像約1,600トークン + 出力300トークン）≒ **$0.003〜0.005** | 月 1,000 枚まで無料、以降 $1.50 / 1,000 枚 | 無料 |
| 月 100 枚登録時の費用 | 約 $0.5（約 75 円） | 0 円（無料枠内） | 0 円 |
| 月 1,000 枚登録時の費用 | 約 $5（約 750 円） | 0 円（無料枠内） | 0 円 |
| 月 5,000 枚登録時の費用 | 約 $25 | 約 $6 | 0 円 |
| API キー管理 | サーバー側で必要 | サーバー側で必要 | 不要 |
| 差し替え容易性 | 高（プロンプト変更のみ） | 中 | 中 |

**整理**: 費用は、個人〜数十人規模ではどの方式も月数百円未満で誤差の範囲。差が出るのは **精度と実装工数** で、A が最も工数が小さく、味覚チャートやカード裏の日本語説明文まで一度に構造化できる。B は無料枠が大きいが、項目振り分けのパーサをカードのレイアウトごとに書く必要があり、ロースターが変わるたびに保守が発生する。C は完全無料だが、スマホで斜めに撮った写真への精度が低く「結局手で直す」になりやすい。

**実装方針（A で確定）**:

- モデル: `claude-haiku-4-5`。表・裏 2 枚を 1 リクエストで送る。
- 出力: Zod スキーマに対応する JSON（各項目 `{ value, confidence }`）。`tool_use` の構造化出力を使い、自由文で返させない。
- 画像はブラウザ側で長辺 1,600px に圧縮してから送る（1 枚 ≒ 1,600 トークン）。
- 生出力は `beans.ocr_raw` に保存し、抽出失敗の再現・プロンプト改善に使う。
- API キーは Vercel の環境変数に置き、`/api/ocr` からのみ呼ぶ。1 ユーザーあたり 1 日 50 回の上限を設け、費用暴走を防ぐ。
- 費用が問題になったら「Gemini Flash 系など、より安価なマルチモーダル API へ切り替え」または「B + 自前パーサ」へ、`OcrProvider` の差し替えで移行する。

### 8.2 店候補・ジオコーディングの比較

| 観点 | A. Google Places / Geocoding | B. OpenStreetMap Nominatim + Overpass |
|---|---|---|
| 現在地周辺の店候補 | Places Nearby / Autocomplete。精度・網羅性が高い | Overpass で `amenity=cafe` を検索。個人店の登録漏れあり |
| 店名→座標 | Geocoding / Text Search | Nominatim。日本の店名検索は弱め |
| 料金（2026-09 時点） | 各 API 月 10,000 回まで無料。超過は Autocomplete $2.83 / 1,000 回、Place Details（Essentials）$5 / 1,000 回、Text Search（Pro）$32 / 1,000 回 | 無料（公開サーバーは 1 req/秒の利用ポリシー。商用・高頻度は自前ホスト推奨） |
| 個人利用での想定費用 | 0 円（無料枠内） | 0 円 |
| 地図タイルとの組み合わせ | Google Maps JS（月 10,000 ロードまで無料）と組むのが自然だが、Leaflet + OSM タイル上に Places の結果を置くことも規約上可（Places データの表示制約に注意） | Leaflet + OSM タイルと自然に組み合わさる |
| API キー | 必要（リファラ制限をかけてサーバー経由に） | 不要 |

**決定（2026-09-21）**: 地図描画は **Leaflet + OSM（無料・キー不要）**。店候補は **まず B（無料）で作り、精度に不満が出たら A に差し替え** る。ただし A・B のどちらでも出てこない店があるため、**店名・住所の手入力と地図タップでの位置指定（F-SHOP-6/7）を Must** とし、候補検索はあくまで入力補助と位置づける。A に切り替えても月 10,000 回の無料枠は個人〜数十人規模なら超えない見込み。

### 12.1 整理

| 観点 | 既存アプリの状況 | 本アプリの位置づけ |
|---|---|---|
| カード/袋のスキャン | Siip・BrewLab など海外勢は AI スキャンを持つ。国内アプリには無い | 国内のテイスティングカード（日英混在、味覚チャート）を前提にした抽出 |
| 店タグ + 地図 | カフェ探し系（Beanhunter）は地図があるが豆記録が無い。記録系は地図が無い | **「自分が飲んだ店の地図」** を豆記録と結ぶのは空いている |
| 自宅抽出・焙煎 | Beanconqueror が圧倒的に詳しい | 同じ深さは狙わず「星とメモだけでも残せる」軽さを優先。詳細レシピは折りたたみ |
| 統計 | Siip の「マッチ率」が近い | 高評価豆の産地・精製・味覚チャート傾向の可視化 |

**結論**: 「豆の記録」単体では競合が多い。差別化の核は **①国内カード向けスキャン、②店タグ×地図、③店でも自宅でも同じ軽さで記録できる** の組み合わせ。Beanconqueror のような抽出パラメータの網羅は追わない。

## 13. ネイティブアプリ化の方針

**方針**: Phase 0〜5 は PWA として開発・運用し、要件が安定した後に **Capacitor** で同じコードを iOS / Android アプリとして配信する。書き直しは行わない。

### 13.1 PWA で足りるもの・足りないもの

| 要素 | PWA | ネイティブで得られるもの |
|---|---|---|
| カメラ撮影 | 標準カメラ起動で可 | アプリ内の撮影ガイド枠、連続撮影 |
| 現在地・地図 | 可 | — |
| ホーム画面アイコン | 可（iOS は手動追加が必要） | ストアからインストール |
| 写真アプリの共有シートから登録 | 不可 | 可（Capacitor プラグイン） |
| プッシュ通知 | 可（iOS 16.4+） | 可（本アプリでは優先度低） |
| ストアでの発見・信頼感 | 無し | 有り |

### 13.2 今から守る設計制約（ネイティブ化のための前提）

| # | 制約 | 理由 |
|---|---|---|
| N-1 | フロントは静的出力（`output: 'export'`）できる構成にする。サーバーコンポーネントに依存する画面を作らない | Capacitor は静的な Web 資産を包む。Next.js のサーバー機能はアプリ内に入らない |
| N-2 | `/api/ocr` `/api/geo` などのサーバー処理は、環境変数 `NEXT_PUBLIC_API_BASE_URL` の絶対 URL で呼ぶ | アプリ内からは Vercel 上の API を叩くため、相対パスでは届かない |
| N-3 | 認証のリダイレクト URL をカスタムスキーム（`coffeelog://`）でも受けられるようにしておく | ストア版のマジックリンク・OAuth 戻り先 |
| N-4 | ブラウザ固有 API（`navigator.share`、Geolocation、カメラ）は `src/lib/platform/` の薄いラッパー経由で呼ぶ | Capacitor プラグインへの差し替えを 1 箇所で済ませる |
| N-5 | 画像は Blob として扱い、`File` 入力に依存する処理を UI 層に閉じ込める | ネイティブカメラプラグインは Blob/base64 で返す |

### 13.3 ネイティブ化時に必要になるもの

- Apple Developer Program（年 99 ドル）、Google Play デベロッパー登録（初回 25 ドル）
- アプリアイコン・スクリーンショット・プライバシーポリシーページ
- 共有シート対応プラグイン（`capacitor-share-target` 相当）と、受け取った画像を記録作成ウィザードへ渡す導線
